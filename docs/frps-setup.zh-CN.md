# 远程 frps 配置

[English](frps-setup.md)

Webtop Manager 可针对两种远程 Linux 服务器场景生成隔离的 frps 部署方案。先在
**服务器设置**中保存服务器地址、公网地址和 frpc 镜像，然后选择
**打开 frps 配置指南**。在指南中选择 frps `bindPort` 和远程端口范围，再选择
**生成命令**。应用会先把所选端口保存到客户端设置，再请求生成命令，从而确保
frpc 与 frps 使用相同的值。之后只要修改端口，旧命令便会隐藏，直到重新生成。
两种部署方式都不会读取、编辑、停止或重启无关的已有 frps 服务；重复运行命令只会
更新并重启此前由 Webtop Manager 创建且带有管理标记的专用实例。

## 使用 Docker 的新服务器

Docker 脚本会：

- 创建 `/opt/webtop-manager-frps/frps.toml` 和权限为 `0600` 的 Token 文件；
- 使用主机网络，在专用的 `webtop-manager-frps` 容器中运行官方
  `ghcr.io/fatedier/frps:v0.70.1` 镜像；
- 将容器标记为 Webtop Manager 所有；如果同名容器不带这些管理标签，则拒绝替换；
- 配置所选的 `bindPort` 和 `allowPorts` 范围；
- 安装与本地 frpc 服务相同、由应用自动生成的认证 Token；
- 启动后输出最初的 frps 日志。

## 不使用 Docker 的新服务器

原生安装脚本支持 Linux x86_64 和 arm64。它会下载固定版本的 frp 发布压缩包，
校验 SHA-256，将 `frps` 安装到 `/opt/webtop-manager-frps-native`，并创建受限的
`webtop-frps` 系统用户。配置和权限为 `0600` 的 Token 文件位于
`/etc/webtop-manager-frps`；专用的 `webtop-manager-frps.service` systemd 单元
负责启动服务并设置开机自启。脚本会先使用 `frps verify` 校验配置，然后启用并
显式重启服务，确保恢复后的 Token 立即生效。
如果同名服务单元或配置目录没有 Webtop Manager 标记，脚本会拒绝覆盖。

远程服务器必须使用 systemd，并提供 `curl`、`tar` 和 `sha256sum`。其他架构需要
从 frp 官方发布页面手动下载匹配的压缩包，并据此调整同一套服务配置。

## 共享端口安全

进程和文件系统隔离无法让两个服务绑定相同的网络端口。运行任一脚本前，请选择
未占用的 frps 绑定端口，以及不与任何现有 frps 代理重叠的远程端口范围。生成的
脚本绝不会为了处理冲突而修改现有服务；在端口调整前，Webtop Manager 专用服务
将无法启动或发布。

生成的安装和 Token 命令包含认证 Token。请只在可信的服务器终端中运行，不要将其
保存在工单、聊天消息、提交到源码仓库的 Shell 脚本或公开日志中。

## Token 持久化与恢复

应用只在首次使用时生成一次 Token，并保存在当前用户的应用数据目录中。普通升级、
卸载安装包和重新安装不会删除这些用户数据，因此会继续复用原 Token；界面不提供
日常 Token 轮换功能。

控制器只在 SQLite 中保存 Token 的 SHA-256 指纹。如果受保护的 Token 文件被删除、
替换或清空，控制器不会静默生成新 Token，也不会启动 frpc，而是在服务器设置中
显示恢复流程。恢复只生成一个固定的新凭据，重复打开或重试不会再次变化；用户重新
运行受管 frps 命令后，认证连通性测试成功才会完成恢复。如果备份了原 Token，直接
恢复同一个权限为 `0600` 的文件即可避免修改远端。

## 防火墙规则

生成的命令不会修改防火墙规则。请允许客户端机器访问配置的 frps 绑定端口，并
允许预期的 Webtop 用户访问配置的远程 TCP 端口范围。若同时使用云服务商安全组和
主机防火墙，需要在两处分别配置规则。

## 验证

返回**服务器设置**，选择**测试连接**。测试会启动一个临时、受限的 frpc 容器，
并真实地向 frps 发起认证登录。成功结果可以验证 DNS/地址解析、TCP 可达性和共享
认证 Token，但不会验证每个远程发布端口；这些端口仍受 `allowPorts` 和防火墙
规则影响。

测试成功后，可在同一页面启动常驻 frpc 服务。状态面板支持启动、重启、停止和
定期刷新 Docker 状态。
